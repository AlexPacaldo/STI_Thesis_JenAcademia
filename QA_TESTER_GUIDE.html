01 · Start safely

Purpose and test setup

Use this guide to validate the user-visible workflows in JEN Academia. Test only on the QA/demo deployment that the project owner has approved. Page names or button labels may vary slightly by screen size.

Demo credentials: the accounts and shared password below are dummy credentials for the seeded demo only. Never use them on a public or production site, and never enter real student information during testing.

Before you begin

  1. Get the approved QA site address and confirm that it is not production. Do not infer the correct host from the sample email domain.
  2. Use a current desktop browser. Record the browser and operating system if reporting an issue.
  3. Sign in with one role at a time. Use a separate private/incognito window or sign out when switching between test users.
  4. Check that the demo dataset is present before following data-dependent scenarios. A scenario may be unavailable if the sandbox has been reset or edited.
  5. Use only test images and text. Do not upload sensitive files, real recordings, or real personal information.
No database reset required: run tests against the already-prepared QA data. Do not wipe, reseed, or edit the database unless the project owner has explicitly approved it and confirmed the target is disposable.

Sign-in and role check

Use the role option shown at the sign-in entry point (Student / Teacher or Admin), then enter the account email and shared password. Confirm the displayed name, role-specific Home page, and navigation menu before testing.

First-time setup differs by role: the seeded accounts may already have completed setup. To test a truly new setup, have the owner create a dedicated QA-only account and provide a fresh setup link; do not reset an existing demo account just to reach onboarding.

03 · Student scenarios

Student / learner test checklist

Use a student account that has an authorized LINE link. If no test student is linked, record that prerequisite as blocked rather than treating the access gate as a failure.

ST-01 · Student access and onboarding

Steps Sign in as a student with an incomplete profile or disconnected LINE account. Follow the setup prompt, upload a test profile picture if asked, confirm the name and time zone, then connect LINE using the authorized test setup.

Expected Student setup requires LINE before it can finish. After completion, the student reaches Home. If LINE is later disconnected, the app requests reconnection before protected student pages are used.

ST-02 · Book a class

Steps Open Calendar → Book a class. Select an available date and time, check the teacher/course details, submit, and revisit Calendar.

Expected The booking is shown in the schedule. A slot that is not available or conflicts with an existing class cannot be booked. Do not use an actual class slot unless the owner has designated it for testing.

ST-03 · Request a reschedule

Steps Select an upcoming class that has not started, request a free alternative time, provide a reason of at least five characters, and submit. Check notifications and the class entry.

Expected The request is pending and the original time remains active until the other participant approves it. It cannot be made or approved after the teacher starts the class. There is no separate advance-notice cutoff configured by this rule.

ST-04 · Contract and class balance

Steps Review the displayed package and remaining classes. If using a dedicated test student, open a new contract request and inspect the class-count options and required course/preferences. If eligible, inspect the extension request flow.

Expected New contract options are 10, 15, or 20 classes. An extension is a request for administrator review, not an automatic change. Avoid submitting duplicate requests unless testing revision behavior.

ST-05 · Learning materials and assignments

Steps Open an available book and lesson. Review saved reading progress, mark a lesson complete where appropriate, then open an assignment, submit a test response, and review its status.

Expected Only assigned materials appear; lesson progress and assignment submission status update without exposing another student's work.

04 · Teacher scenarios

Teacher test checklist

TE-01 · Staff first-time setup

Steps Use a dedicated fresh QA teacher account. Follow setup, add a test profile picture, review the name and time zone, and continue.

Expected A profile picture is required for first-time setup. Phone verification and LINE linking are not required for teacher setup. The account proceeds to its teacher Home page.

TE-02 · Profile, students, and permissions

Steps Open Account and My students. Review the teaching profile, experience, specialization, course, and assigned learners. Compare with the seeded fixture reference only if needed.

Expected The profile fields that exist for the account display correctly. The teacher sees assigned students and does not gain access to unrelated student records.

TE-03 · Class and reschedule workflow

Steps Open an upcoming test class, inspect its details, then review the pending reschedule request if available. Approve or reject only within the sandbox; when rejecting, enter a reason of at least five characters.

Expected The class schedule reflects an approval; a rejection preserves the original schedule and communicates the reason. Once the class has started, the request can no longer be decided.

TE-04 · Class completion

Steps Use a dedicated test class only. Review consent, join the meeting, capture a non-sensitive test recording if the owner approved it, add a complete class summary and learner remark, then complete/verify the class.

Expected Required recording upload and written details are accepted; the completed class appears in history. Recordings are temporary and deleted after seven days. Do not record real people or conduct an unapproved recording test.

TE-05 · Assignments, reviews, and books

Steps Create an assignment for a test student, submit it from the student account, then review/grade it as the teacher. Check contract reviews and My books for the expected student/course material.

Expected Each role sees the correct task state and permitted materials; teachers can read assigned books and monitor progress but do not manage the shared library.

05 · Administrator scenarios

Administrator test checklist

AD-01 · Staff first-time setup and role routing

Steps Use a dedicated fresh QA administrator account and complete setup with a test profile picture. Navigate through the dashboard areas available to that account.

Expected Setup does not require phone verification or LINE. Admin Home and admin-only navigation are shown. Super-admin-only actions appear only when permitted.

AD-02 · Account and contract management

Steps Find a test account in Account Management, review the profile and package, and use only owner-approved changes. Inspect pending contract requests and their detail.

Expected Account and request details match the selected student; completed account setup removes invite resend/copy actions and the email is read-only. Package sizes available in forms are 10, 15, and 20.

AD-03 · Requests and calendar visibility

Steps Review Calendar and the Requests area for the test classes and pending requests.

Expected Admin can inspect request status and schedule information, but cannot approve or reject participant reschedule requests.

AD-04 · Books, lessons, and access distribution

Steps In Books / Lessons, create a test book and lesson, distribute it to a test teacher, verify access as the teacher/student, then archive and restore the test book if those actions are in scope.

Expected Admin owns the shared library; teachers and students see materials only where access is granted. Archiving hides a book while preserving restore capability.

AD-05 · Reviews and attendance verification

Steps Inspect Contract reviews and Verifications using the seeded examples or dedicated test classes.

Expected Submitted reviews and class evidence show their actual status. A pending review remains pending until evidence is checked; do not mark a class verified without the required evidence.

Cleanup: remove or archive only records created specifically for QA and only when authorized. Never hard-delete seeded data or modify account roles, passwords, assignments, classes, or contracts without the owner's approval.
06 · Report results

Recording and reporting defects

For every test

  • Mark each scenario Pass, Fail, or Blocked. Explain blocked prerequisites, such as no authorized test LINE link or no available test class.
  • Record the test date/time and time zone, browser/version, device/OS, role, and the specific demo account name (do not include its password in a bug report).
  • For a failure, include the exact page, clear reproduction steps, expected result, actual result, and whether it happens every time.
  • Attach a screenshot or short screen capture when useful. Crop or blur passwords, linking codes, email content, personal data, and unrelated accounts.
  • Do not report expected safeguards as defects: student LINE gating, role-based menus, pending reschedule approval, unavailable slots, and pending evidence review are intentional behavior.

Suggested severity

LevelUse when…
CriticalCore service is unavailable, data is lost/corrupted, or an account can access another user's sensitive information.
HighA major workflow is blocked for a role and there is no reasonable workaround.
MediumA feature is incorrect or unreliable but a workaround exists, or important information is confusing.
LowMinor visual, wording, or alignment issue with no material workflow impact.

Defect report template

Title: [Role] concise description

Environment: QA URL, browser/version, device/OS

Account: role and sample account name (never the password)

Preconditions: relevant account/data state

Steps to reproduce: numbered actions

Expected: what should happen

Actual: what happened, including any visible error

Frequency / severity: always, intermittent, or once; proposed severity and reason

Evidence: sanitized screenshot or recording, if safe

If the result differs from this guide, check the currently deployed build and ask the project owner whether the workflow has intentionally changed before filing a defect.
