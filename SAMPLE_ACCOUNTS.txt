 9. HOW TO RUN
--------------------------------------------------------------------------------

  1. Reset only the disposable demo database. Keep the application schema.
     The seeder creates the nine required courses if they are missing, but it
     does not create tables or drop existing data. Never point it at live data.

  2. Seed the accounts:

         cd backend
         node seed-demo-data.mjs

     It lives in backend/ rather than scripts/ on purpose. It needs dotenv,
     bcryptjs and mysql2, and Node resolves those by walking UP for
     node_modules - which this repo has only in backend/. From scripts/ those
     three imports fail with ERR_MODULE_NOT_FOUND.

     It reads backend/.env and resolves credentials exactly the way the server
     does - DB_*, then MYSQL*, then a parsed MYSQL_URL or DATABASE_URL, which is
     what Railway provides. So point it at Railway the same way you point the
     server at Railway: MYSQL_URL in backend/.env, or the DB_* variables.

     It prints what it resolved before it connects, so check that line says your
     Railway host and not "localhost". A seed that quietly resolved to localhost
     would write to your own machine, so it refuses and tells you to pass
     ALLOW_LOCAL_DB_SEED=1 if that is genuinely what you want.

     !! Railway gives out TWO URLs for one database, and this script needs the
     !! other one from the app. The app runs inside Railway, so it uses the
     !! private address that only resolves on Railway's own network
     !! (mysql.railway.internal). This script runs on YOUR machine, where that
     !! name never resolves - the driver just waits on DNS until it times out,
     !! with no error to tell you the hostname itself was the problem.
     !!
     !! So in backend/.env, for seeding only, use the PUBLIC URL from the Railway
     !! dashboard (MySQL service > Networking > public domain). Leave the
     !! deployment itself on the internal one, which is correct there.
     !!
     !! Also check the database name it prints. Railway's default is "railway",
     !! not "jen_academia"; whichever your deployment actually uses is the one
     !! that must match, and the seeder only warns you about this rather than
     !! guessing.

     It is safe to re-run - it updates the same rows rather than duplicating.

     !! No server restart is needed afterwards, and this used to be the most
     !! easily missed step in the whole demo. The Expires column on this page
     !! stays blank until every package has a deadline on it, and a blank
     !! column is indistinguishable from a feature that was never built. The
     !! seed used to write expires_at as NULL on purpose, expecting the server
     !! to derive it on its next boot - so it depended on a redeploy happening,
     !! and re-running the seed actively cleared a deadline the server had
     !! already set.

     The seed now writes the deadline itself, using the same rule the server
     would, and then reads every package back and prints a table of them. If a
     deadline is ever missing again it says so loudly rather than finishing on
     trust.

     In addition to accounts and matching scenarios, the seeder adds books,
     published lessons, lesson progress, pending/submitted/graded assignments,
     a completed class with a remark, a separate attendance record awaiting
     review (with no fabricated proof), and a pending reschedule request.
     Initials avatars satisfy profile setup. Real LINE
     identities and video-provider credentials are never fabricated.

     What is NOT seeded is the package status. A package past its term is flipped to
     "expired" by the running server's own 60-second sweep, so the expiry you
     demonstrate is the real mechanism rather than an edited value. Expect
     Danica to read "expired" and Carlos to carry the warning within a minute
     of seeding, with no redeploy.

  3. START THE SERVER ONCE, then stop it.

     This matters. The first boot is what:
       - derives each contract's expires_at from created_at (3 months)
       - encrypts the seeded notes and birth dates
       - flips Danica's package to 'expired', because the rule says so

     Without that boot you will see no expiry dates.

  4. Sign in as admin@jenacademia.local / JEN2026!

  5. Work through section 7 in order.

 10. IF SOMETHING LOOKS WRONG
--------------------------------------------------------------------------------

  "No teachers matched" on Ava
      Check Rafael and Maia are assigned to Conversational English
      (Teacher Courses, admin side). The candidate pool is by COURSE.

  No expiry dates anywhere
      The server has not booted since you seeded. Do step 3.

  "No active students found" on Contracts
      The seed inserts students directly with profile_completed = TRUE. If you
      created your own students through the form they are still FALSE until they
      finish their setup invite, and this screen will not list them.

  The AI section says nothing
      GEMINI_API_KEY / GOOGLE_GEMINI_API_KEY is not set in production. The
      rules-only path is working correctly - that is Step 8's fallback.

  Clara Reyes looks like a bug
      She is deliberate. A thin profile is the honest way to make the
      "closest available, not a strong match" state reachable.

  The birthday in the profile page does not match section 1
      Birthdays are stored encrypted, so they cannot be read from SQL. Check the
      UI, and re-run the seed if the profile page really disagrees.
